# 扩展系统（初步方案）

## 目标

扩展系统的目标不是替代主题，而是在固定主题之上提供类似创意工坊的内容能力：

- 游戏运行中热切换
- 第三方内容无需重新编译主游戏
- 多个扩展可以同时影响不同玩法面向
- 扩展运行在受限沙箱中，不得直接破坏核心状态

完整游戏的组成关系为：

- `core` + `theme` + `extensions`

其中：

- `core` 提供稳定数据模型、基础规则与未来扩展点
- `theme` 决定题材包装与编译期固定的玩法基底
- `extensions` 在运行时装配额外内容

## 扩展类型

初步纳入的扩展类型：

- 群体智能算法与演化策略
- 新兵种与单位规则
- 地图生成器
- AI 行为树或任务控制器
- HUD 面板与观察工具
- 局部规则模块，例如额外资源系统、事件系统、胜利条件

一个扩展可以同时覆盖多个方面，例如：

- 新兵种 + 对应演化规则
- 地图生成器 + 新的占点规则
- AI 行为树 + HUD 调试面板

## 运行模型

目标运行模型：

- 扩展以 WASM 模块形式加载
- 扩展在沙箱环境中执行
- 优先使用 `Spore` 作为扩展编写语言，再编译为可加载产物
- 扩展可在运行中启用、停用、替换

这意味着扩展系统需要一个独立的 host 层，而不是直接把 Bevy `Plugin` 暴露给第三方。Bevy `Plugin` 适合仓库内部静态组装，不适合承担创意工坊式的运行时加载、隔离和版本管理职责。

## Host 侧职责

未来的扩展 host 需要至少负责：

- 扩展发现与注册
- 生命周期管理（加载、启用、停用、卸载、热切换）
- API 边界与权限控制
- 数据交换与序列化
- 版本兼容检查
- 错误隔离与崩溃恢复

## Core 需要提供的扩展点

`core` 不直接承载具体扩展实现，但需要逐步整理出稳定扩展点，例如：

- 单位生成钩子
- 地图生成接口
- 行为决策接口
- 事件订阅与派发接口
- HUD 数据读取接口
- 规则覆写或附加规则接口

这些扩展点更适合作为受控 API，而不是让扩展直接访问 ECS 全量世界状态。

## Theme 与 Extension 的边界

边界约定：

- 主题是编译期固定的整体包装
- 扩展是运行时可替换的玩法内容
- 当前主题专用算法可以先直接实现到 `theme` 中
- 当某类玩法经过验证后，再抽象成稳定扩展点

这也是当前阶段的策略：

- 先把 Grey Wolf Optimizer 直接集成到 `hive-war`
- 暂不把它抽成扩展
- 等扩展 API 足够稳定后，再决定是否把群体智能算法族迁移为扩展类型

## 约束与隔离

扩展系统的安全边界初步要求：

- 扩展不能任意读写所有 ECS 状态
- 扩展不能直接访问宿主文件系统或网络
- 扩展只能通过显式授权的 host API 读写游戏状态
- 热切换时需要有状态迁移或状态丢弃策略

## 待办

- 明确扩展清单格式与元数据规范
- 设计扩展发现、安装、启用与卸载流程
- 设计 host API 的版本策略
- 决定扩展状态如何序列化与迁移
- 明确哪些能力是只读观察，哪些能力允许写入
- 评估 `Spore -> WASM` 的工具链形态与调试体验
- 决定扩展包是否需要签名、权限声明或能力清单
- 决定热切换失败时的回滚模型
- 梳理哪些现有主题系统未来适合抽象成扩展点

## 当前结论

扩展系统先停留在设计层，不进入本轮实现。

本轮实现只做两件事：

- 调整项目结构认知为 `core` / `theme` / `extensions`
- 在当前 `hive-war` 游戏中直接接入一个具体群体智能算法
