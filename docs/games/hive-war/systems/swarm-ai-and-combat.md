# 蜂群 AI 与战斗

## 移动层

- **全局流场**：决定大方向推进目标。
- **局部分离**：避免单位重叠，保证视觉可读性。
- **信标力场**：给玩家提供宏观干预手段。

当前移动向量由三部分混合：

- 基础推进方向
- 同阵营分离力
- 信标附加力

当前还额外加入了一层**局部胜算评估**：

- 单位会估算感知范围内己方与敌方的局部战力。
- 局部战力的基础强度由单位属性统一换算（伤害、耐久、机动、感知共同构成），不再只看单一攻击值。
- 若判断敌方明显占优，单位不会继续无脑追击，而会优先脱离敌群并向己方群体回靠。
- 若局部兵力尚可承受，单位才继续执行推进与追击。

**移动与接战惯性**：

- 合成后的期望移动方向会按帧平滑，避免流场、分离、追击之间来回打架导致抖动。
- 追击目标在感知范围内会短暂锁定；只有出现明显更近的敌人才会切换目标，减少目标来回跳变。

## 战斗层

- 单位进入感知范围后开始计算伤害。
- 伤害带有距离衰减，避免所有单位无脑堆在一起输出等效。
- 护甲提供平滑减伤，降低数值波动。

### 目标优先级（基地 vs 单位）

同一帧内，每个单位**要么**对可占领基地施加占领伤害，**要么**参与单位互伤，不会两边同时输出：

- 若武器范围内存在**敌对单位**，则本帧只参与单位战，不占压基地血量。
- 若武器范围内没有敌对单位，且站在**可 assault 的基地**占领半径内，则本帧只产生基地占领伤害，不产生对单位的**Outgoing** 伤害（仍可作为目标被攻击）。

## 性能层

- 使用空间哈希代替全量两两碰撞。
- 使用固定尺寸流场网格，避免单体 A*。
- 大部分行为依赖群体规则，而不是复杂单体决策树。

## 表现层

- 进化职业通过多边形轮廓区分。
- 单位外轮廓的**面积**与同一套属性强度模型成正比；因此升级或基因变强后，单位会自然变大，而半径按 `sqrt(strength_ratio)` 缩放，保证面积才是主要表达量。
- 视觉体积、击杀价值、以及局部敌我强弱判断共用同一套强度基础，避免“看起来弱但判定很强”或相反的错位。
- 死亡与融合事件通过粒子强调关键反馈。
- HUD 用于观察群体状态，而不是承载复杂操作。

## 战术小队与队长（两层决策）

与 [`wolf_pack`](../../../../crates/hive-war/src/plugins/wolf_pack.rs) 里用于**跨代遗传**的 Grey Wolf Optimizer（alpha/beta/delta **基因引导**）不同，**战术小队队长**解决的是同一场战斗内的编队与目标分配问题：

- **群体层**：仍以纯算法为主（流场、分离、追击、以及既有或后续的群体优化器），高频率（例如每帧）在 ECS 中更新每个单位的运动。
- **队长层**：低频（例如约 10Hz）在少数「队长」实体上产出战术意图（目标点、阵型倾向、攻守权重等），再被群体层消费。

队长数量与归属由共享 `swarm-tactics` 中的**公式驱动**逻辑计算（预期小队数 K、带压制半径的头狼选举、加权距离归属等），与渲染无关，便于测试与复现。

## 无渲染模拟与数据集（Headless）

目标：在**不打开窗口、不跑渲染管线**的前提下，批量生成可复现的样本，供模仿学习或后续强化学习使用。

### 放在共享 crate 的原因

- **核心规则与 ECS 模型**在 `swarm-model` / `swarm-space` / `swarm-tactics` / `swarm-growth` / `swarm-sim`，**游戏包装**在 `hive-war`（见 [`../../../architecture/overview.md`](../../../architecture/overview.md)）。数据集合同、小队公式、无渲染仿真入口属于共享层职责，避免游戏 crate 反向依赖或重复实现一套仿真。
- 主题若只增加仍落在 core 组件/资源上的字段，headless 世界可与正式游戏共用同一套类型。

### 已实现能力（概要）

- **纯算法路径**：`squad` 模块（K、压制半径 R、NMS 头狼选举、λ 加权归属等）。
- **数据集 schema**：`captain_dataset`（版本号 `schema_version`、固定维特征与标签占位、JSON Lines 行格式）。
- **二进制 `swarm-record`**：默认 **Phase 1** 为纯 Rust 合成模拟 + 写盘；**不依赖**完整 Bevy。
- **可选 `sim_bevy` feature**：在 core 内用 **MinimalPlugins**（无窗口）+ `Transform` 等挂载与游戏一致的组件，从 ECS 填快照后写入**同一套** JSONL，用于提高样本与真实对局的结构一致性。

### 与带渲染客户端的关系

- **`hive-war`**：继续作为带 `DefaultPlugins`、HUD、粒子的可玩入口。
- 若将来需要「边玩边录」，可做薄封装：调用 core 提供的记录逻辑或复用 `swarm-record` 的写出路径，而不必在主题里再实现一套公式。

## 学习与训练路线（模仿学习为主，强化学习可选）

### 推荐顺序（工程上最省事）

1. **模仿学习（行为克隆）**：用专家策略（脚本 bot、人类录像或 headless 里的占位专家）产生 `(特征 → 动作)`，在 Python 侧用 PyTorch 等训练小型 MLP，再导出 **ONNX**。
2. **部署**：游戏内用轻量 ONNX 推理（例如 `tract-onnx`）只在**队长**上跑，群体层仍纯算法，保证 WASM/CPU 预算可控。
3. **强化学习（可选）**：在 **headless** 环境中暴露与正式对局一致或近似的状态转移与奖励（同一套共享规则 crate），在 Python 或专用 RL 框架里训练；收敛后同样 **导出 ONNX 替换权重**，Rust 侧接口可保持稳定。

### 强化学习与 headless 的分工

- **Headless**：提供**可批量运行、可确定性种子、无 GPU 渲染负担**的仿真与采数管道，是 IL/RL 数据集与共用的「仿真后端」抽象。
- **RL 本身**：不强制在 Rust 内实现；更务实的是 **headless 仿真 + 外部训练 + ONNX 回灌**。若日后需要在 Rust 内嵌短_rollout，仍应以共享规则 crate 为单一事实来源，避免与 `hive-war` 渲染逻辑耦合。

### Python 训练与 ONNX（仓库内工具）

- 目录：[`tools/captain_train/`](../../../tools/captain_train/README.md)（`uv` + `train_bc.py`）。
- **行为克隆**：读取 `swarm-record` 产出的 JSONL，训练 MLP，导出 **ONNX**（`input`/`output` 名称与张量形状与 `captain_dataset` schema v1 对齐，便于 `tract-onnx` 加载）。
- **fixture**：`fixtures/tiny.jsonl` 用于快速冒烟；正式训练请用 `swarm-record` 生成足够样本。
- **强化学习**：不在该目录内置完整环境；见同目录 README 中「RL」扩展方式（外部 RL 框架 + 同一 ONNX 接口）。

### 与遗传层的关系

- **遗传 / GWO（`wolf_pack`）**：慢时间尺度，作用于基因与代际。
- **队长策略（MLP/ONNX）**：快时间尺度，作用于单局战术意图。
两者不应混在同一套「alpha/beta/delta」命名下，以免策划与代码读者混淆。
